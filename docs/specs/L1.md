# L1 - High-Level Requirements

These requirements were reverse-engineered from the existing Angular SPA + .NET 9 modular monolith implementation, the detailed designs in `docs/detailed-designs/`, and the UI design in `docs/ui-design.pen`. The guiding constraint is **radical simplicity**: every capability must be deliverable as a small vertical slice with no speculative abstractions.

## Functional Capabilities

### L1-001: User Authentication
The system must allow a user to sign in with a username and password, must issue a session token used for all subsequent API calls, and must allow the user to sign out.

### L1-002: Profile Management
A user must be able to own one or more profiles, must be able to switch the active profile, and all domain data the user creates must belong to exactly one profile.

### L1-003: Behaviour Catalog
The system must allow a user to maintain a catalog of behaviours (e.g., "Drink 2L water") classified by behaviour type. Behaviours are the building blocks referenced by commitments and activities.

### L1-004: Frequency Catalog
The system must allow a user to maintain a catalog of frequencies (e.g., "Daily", "3x/wk", "Weekly") classified by frequency type. Frequencies are referenced by commitments to express how often a behaviour is expected.

### L1-005: Commitment Tracking
A user must be able to define commitments that pair a behaviour with one or more frequencies and optional pre-conditions, and must be able to view, edit, and remove their commitments.

### L1-006: Activity Recording
A user must be able to record an activity (an instance of performing a behaviour at a point in time) and must be able to review their activity history.

### L1-007: Note Management
A user must be able to create, edit, tag, list by tag, and delete rich-text notes.

### L1-008: To-Do Management
A user must be able to create, edit, complete, and delete to-do items.

### L1-009: Digital Asset Management
A user must be able to upload, reference, and retrieve digital assets (e.g., images used by dashboard cards or notes) tied to their profile.

### L1-010: Configurable Dashboard
A user must have a personal dashboard composed of cards. The user must be able to add, configure, reorder, and remove cards from a fixed catalog of card types (Daily Results, Weekly Focus, Monthly Progress, Outstanding To-Dos, Relations, Poster, Streak, Notes, etc.).

### L1-011: Live Dashboard Mode
The dashboard must support a Live mode that streams real-time updates of commitment/activity progress to the user without page refresh, with a visible "LIVE" indicator on each live tile.

### L1-012: Review Dashboard Mode
The dashboard must support a Review mode that lets the user pick a date window and scrub a slider to see what each tile's value was at any chosen instant in the past. Review mode is read-only.

## Application Shell & Presentation

### L1-013: Application Shell & Navigation
The application must present a persistent shell consisting of a top toolbar with the app title and current user, a left sidenav listing primary destinations (Dashboard, Commitments, Notes, To-Dos, Settings, Logout), a primary page header, and a floating action button on pages where a primary create action exists.

### L1-014: Dark-Theme Visual Design System
The system must render in a single dark theme using the design tokens, typography scale, and Material component variants defined in `docs/ui-design.pen` (the `Design System` frame). All visual primitives — buttons, FABs, inputs, chips, radios, snackbars, dialogs, cards, tiles, table rows, sidenav items — must derive from the catalog of reusable components in that file.

### L1-015: Responsive Layout
Every page must render correctly at four reference breakpoints documented in `docs/exports/INDEX.md`: S (360px), M (768px), LG (1280px), XL (1920px), and must remain usable at any width down to XS (<576px).

### L1-016: Internationalization
All user-visible strings must be sourced through `@ngx-translate/core` so the application can be translated without code changes.

## Cross-Cutting Concerns

### L1-017: Security & Multi-Tenant Data Isolation
Every API endpoint must enforce authentication and must scope all reads and writes to the caller's active profile so that data of one profile cannot be observed or mutated by another. Soft-delete and audit timestamps must be applied uniformly.

### L1-018: Performance & Real-Time Responsiveness
Read endpoints serving the dashboard must return in a single round-trip and must not require client-side fan-out. Live updates must be pushed via the existing SignalR hub. Review-mode scrub queries must be debounced client-side and answered by a single server-side count query.

### L1-019: Modular Vertical-Slice Architecture
The backend must remain a modular monolith composed of independent feature modules (Commitments, Identity, Dashboard, DigitalAssets) sharing only `Commitments.Shared`. Modules must communicate in-process through `IEventBus` and must reference each other only by plain `Guid`. Each user-facing feature must be implemented as a vertical slice (controller + MediatR handler + DTO + FluentValidation validator).

### L1-020: Operational Readiness
The API must expose Swagger UI, must support startup migration and seed via `migratedb seeddb`, and must use `Asp.Versioning.Mvc` for explicit API versioning. FluentValidation must run as a MediatR pipeline behavior so invalid requests fail before reaching handlers.
