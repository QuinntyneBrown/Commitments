# L2 - Detailed Requirements

Each L2 traces to exactly one L1. Acceptance criteria use Given/When/Then so they translate directly into ATDD tests. When acceptance tests are authored, each test file must include a `Traces to:` comment naming the L2 IDs it covers.

---

## Authentication

### L2-001: Username + password sign-in
**Traces to:** L1-001

The login screen (`pages/login`) must collect a username and password, must POST to the auth endpoint via `AuthService.tryToLogin`, and on success must persist the resulting session token plus the user's current `profileId` in local storage.

**Acceptance Criteria:**
1. Given the user is on the login screen, when they submit a valid username and password, then they are redirected to their pre-login destination (or the dashboard if none was captured).
2. Given the user submits an empty username or password, when they tap Submit, then the form is invalid and no request is sent.
3. Given the auth endpoint returns 401, when the response arrives, then a snackbar reads "Login Failed" and the form remains editable.
4. Given a successful login, when the session token is persisted, then the next outbound API call carries an `Authorization: Bearer <token>` header.

---

### L2-002: Sign-out clears session
**Traces to:** L1-001

Logging out (sidenav "Logout" or visiting `/login`) must clear the cached session token and the cached `profileId`.

**Acceptance Criteria:**
1. Given the user is signed in, when they navigate to the login route, then `AuthService.logout()` is invoked on init.
2. Given the user has logged out, when any protected route is requested, then they are redirected to login.

## Profile

### L2-003: Current profile bootstrap
**Traces to:** L1-002

After successful login the system must fetch the user's current profile via `ProfileService.current()` and must store the returned `profileId` under `currentProfileIdKey` in `LocalStorageService`.

**Acceptance Criteria:**
1. Given a successful login, when `ProfileService.current()` resolves, then `LocalStorageService.put({ name: currentProfileIdKey, value: profile.profileId })` is called exactly once.
2. Given the cached `profileId` is present, when any API request is sent, then the `ProfileId` header is set to that value (per `HttpContextAccessorExtensions.GetProfileId()` on the server).

---

### L2-004: Profile CRUD
**Traces to:** L1-002

The Profiles page must list profiles for the signed-in user, must allow creating a new profile via `CreateProfileDialog`, and must allow deleting a profile.

**Acceptance Criteria:**
1. Given the user opens the Profiles page, when the list loads, then only profiles belonging to the signed-in user are shown.
2. Given the user submits the Create Profile dialog with a valid name, when the request succeeds, then the new profile appears in the list without page refresh.
3. Given a profile is deleted, when the delete request returns 200, then the row disappears and any cached references in dashboard cards are not silently broken (dashboard still loads).

## Commitments

### L2-009: Commitment composition
**Traces to:** L1-005

A commitment must be created or edited via `EditCommitmentDialog`, must reference exactly one behaviour, must accept zero or more `CommitmentFrequency` entries, and must accept zero or more named `CommitmentPreCondition` entries.

**Acceptance Criteria:**
1. Given the dialog is open, when the user selects a behaviour and at least one frequency and saves, then the commitment is persisted with the behaviour link and the chosen frequencies.
2. Given the user adds a pre-condition with an empty name, when they save, then validation fails with `Name must not be empty` (FluentValidation `.NotEmpty()`).
3. Given a commitment exists, when the user opens it for edit, then all linked frequencies and pre-conditions are pre-populated.

---

### L2-010: Personal vs daily commitment queries
**Traces to:** L1-005

The API must expose `GetCommitments`, `GetPersonalCommitments`, and `GetDailyCommitments` queries, each returning only commitments owned by the active profile.

**Acceptance Criteria:**
1. Given two profiles each own commitments, when profile A calls `GetCommitments`, then profile B's commitments are not in the response.
2. Given the active profile has a commitment whose frequency includes "Daily", when `GetDailyCommitments` is called on a weekday, then the commitment is included; if the frequency is Weekly only, it is excluded.
3. Given the user opens the Commitments page on LG/XL, when the table renders, then it paginates at 5 rows per page (per `g4y1n.png` design) with "Rows per page" and prev/next controls.

---

### L2-011: Commitment removal is soft
**Traces to:** L1-005

`RemoveCommitment` must perform a soft-delete via `BaseDbContext` (set `IsDeleted = true`, populate `LastModifiedOn`), not a physical row delete.

**Acceptance Criteria:**
1. Given a commitment is removed, when the database is inspected, then the row still exists with `IsDeleted = true`.
2. Given a commitment has been removed, when any list query runs, then the row is filtered out by the global soft-delete query filter.

## Live Mode (Detailed Design 01)

### L2-023: Live tile initial render
**Traces to:** L1-011

`LiveGoalMetricsTileComponent` must, on mount, call `GoalProgressService.getCurrent(goalId)` and must display target, count, and a progress ring (`count/target * 100`, clamped to 0–100).

**Acceptance Criteria:**
1. Given a goal with `target = 30` and current `count = 12`, when the tile mounts, then the ring renders at 40% and the centre reads `12 / 30`.
2. Given the API returns `target = 0`, when the tile mounts, then the tile renders the literal "no target set" instead of dividing by zero.

---

### L2-024: SignalR push updates the live tile
**Traces to:** L1-011

The tile's controller must subscribe to `hubClient.on<GoalProgressUpdated>('goalProgressUpdated')`, must filter events by `goalId`, and must update `count` and `lastUpdatedAt` signals on each matching event.

**Acceptance Criteria:**
1. Given the tile is mounted with `goalId = 17`, when a `goalProgressUpdated` event arrives with `{ goalId: 17, count: 13 }`, then the tile re-renders with count `13` without an HTTP request.
2. Given the event has `goalId = 99`, when it arrives, then the tile ignores it.

---

### L2-025: Hub publication on achievement creation
**Traces to:** L1-011

When an achievement is created, the existing achievement-created integration handler must publish `goalProgressUpdated` to the per-profile hub group `profile:{profileId}` with `{ goalId, count, asOf }`.

**Acceptance Criteria:**
1. Given a user records an achievement against goal 17, when the handler completes, then exactly one `goalProgressUpdated` is sent to group `profile:{profileId}` with the new count.
2. Given the achievement is for a goal owned by another profile, when the handler runs, then no event is sent to the current user's group.

---

### L2-026: Live badge animation
**Traces to:** L1-011

The Live tile must display the `LIVE` badge (per `o0BgI.png` and `A1yim.png`) with a pulsing accent dot whenever Live mode is active.

**Acceptance Criteria:**
1. Given the tile is in Live mode, when the page is loaded, then a `LIVE` badge with a pulsing dot is visible in the tile's top-right corner.
2. Given the user switches the dashboard to Review mode, when the live tile is replaced by a review tile, then the LIVE badge is no longer in the DOM.

## Review Mode (Detailed Design 02)

### L2-027: Review tile date-window selection
**Traces to:** L1-012

`ReviewGoalHistoryTileComponent` must expose two `<input type="datetime-local">` controls (start, end) and an Apply button. Apply must be disabled when start ≥ end or when the inputs are not valid ISO datetimes.

**Acceptance Criteria:**
1. Given the user enters start = `2026-04-01T00:00` and end = `2026-04-30T23:59`, when both inputs are valid and start < end, then `canApply` is true and the Apply button is enabled.
2. Given the user enters start > end, when the controller recomputes `canApply`, then the button is disabled.

---

### L2-028: Slider scrub fetches historical count
**Traces to:** L1-012

When the user drags the slider, the controller must compute `scrubAt = appliedStart + (appliedEnd - appliedStart) * pct/100` and must call `GoalProgressService.getAt(goalId, scrubAt)` debounced 100 ms.

**Acceptance Criteria:**
1. Given the slider moves rapidly across 50 positions in 200 ms, when the dust settles, then no more than 3 HTTP requests are sent (debounce 100 ms).
2. Given a request returns `{ count: 8, asOf: "2026-04-05T14:00:00Z" }`, when the response arrives, then the tile renders count `8` and the date badge shows `Apr 5`.

---

### L2-029: Historical endpoint clamps inputs
**Traces to:** L1-012

`GET /api/goal-progress/at?goalId&asOf` must clamp `asOf` to `(GoalCreatedAt, UtcNow]` and must reject `asOf` that fails ISO-8601 parsing with HTTP 400.

**Acceptance Criteria:**
1. Given `asOf` is in the future, when the request is processed, then it is clamped to `UtcNow` and the response's `asOf` reflects the clamp.
2. Given `asOf = "not-a-date"`, when the controller binds the parameter, then the response is 400.
3. Given the goal does not belong to the active profile, when the handler runs, then the response is 404.

---

### L2-030: Review mode swaps tiles and hides FAB
**Traces to:** L1-012

When the dashboard mode toggle (`A1yim`/`WFYHQ`) switches to Review, the live tiles (`o0BgI`) must be replaced by review tiles (`nAfUX`), the scrubber (`zNLnf`) must appear at the top of the grid, and the FAB must hide.

**Acceptance Criteria:**
1. Given the dashboard is in Live mode, when the user clicks the Review pill, then the FAB is removed from the DOM and the scrubber appears above the tile grid.
2. Given the dashboard is in Review mode, when the user clicks "Jump to today", then mode returns to Live, live tiles return, and the FAB reappears.

---

### L2-031: Review tile delta vs today
**Traces to:** L1-012

Each review tile (`nAfUX`) must show the historical value, a date badge, and a delta-vs-today indicator (e.g., `+1 vs today`, `-1 vs today`) with green for positive and warn for negative.

**Acceptance Criteria:**
1. Given today's count is 10 and the historical count at `asOf` is 8, when the tile renders, then the delta reads `-2 vs today` in warn colour.
2. Given today's count equals the historical count, when the tile renders, then the delta reads `±0 vs today` in neutral colour.

## Security

### L2-038: ProfileId header drives multi-tenant scoping
**Traces to:** L1-017

`HttpContextAccessorExtensions.GetProfileId()` reads `Request.Headers["ProfileId"]` (not from JWT claims). Every module's `DbContext` global query filter must apply this profileId so cross-profile leaks cannot occur even if a feature handler forgets to filter.

**Acceptance Criteria:**
1. Given a request omits the `ProfileId` header, when any profile-scoped endpoint is called, then the response is 400 (or 401 if also unauthenticated), never a successful response with empty data.
2. Given two profiles A and B, when A's token + B's `ProfileId` are sent together, then the API returns 403 (the token's user does not own profile B).

---

### L2-039: Soft-delete and audit on every entity
**Traces to:** L1-017

`BaseDbContext` must intercept `SavingChanges` to set `IsDeleted` on deletes and to populate `CreatedOn` / `LastModifiedOn` on inserts and updates. Every entity inheriting `BaseEntity` participates automatically.

**Acceptance Criteria:**
1. Given any new entity is saved, when the row lands in SQL, then `CreatedOn` is non-null and `LastModifiedOn` equals `CreatedOn`.
2. Given an entity is updated, when the row is re-read, then `LastModifiedOn` is greater than `CreatedOn`.
3. Given any entity is deleted via EF, when the row is inspected, then `IsDeleted = true` and the row still exists.

---

### L2-040: FluentValidation via MediatR pipeline
**Traces to:** L1-017

Every command request must have a `FluentValidation` validator. `ValidationBehavior<,>` in `Commitments.Shared` must run validators before the handler and must throw a 400-mapping exception on failure. Validators on `Guid` fields must use `.NotEmpty()` (never `.NotNull()`).

**Acceptance Criteria:**
1. Given a command with a missing required field, when MediatR dispatches, then the handler is never invoked and the API returns 400 with the validator's messages.
2. Given a `Guid` field has the default value `Guid.Empty`, when validated with `.NotEmpty()`, then validation fails (`.NotNull()` on a struct would always pass and is therefore forbidden).

---

### L2-041: OWASP input hardening on user inputs
**Traces to:** L1-017

All free-text inputs (note body, behaviour name, commitment pre-condition name, etc.) must be persisted as-is but rendered with HTML-escaping on read paths. Quill output stored as HTML must be sanitised server-side before persistence to strip `<script>` and event-handler attributes.

**Acceptance Criteria:**
1. Given the user pastes `<script>alert(1)</script>` into a note, when the note is saved and reopened, then no script tag survives in the DOM.
2. Given a behaviour name contains SQL meta-characters, when listed, then the page renders the literal characters and no query is executed against them.

---

## Performance

### L2-042: Single round-trip for dashboard load
**Traces to:** L1-018

`DashboardService.getByCurrentProfile()` must return the dashboard with all `dashboardCards` (and any inlined options) in one HTTP call. Each card type's data must then be fetched independently by its own component.

**Acceptance Criteria:**
1. Given the dashboard has 8 cards, when the page first loads, then the network panel shows exactly 1 request to `/api/dashboards/current` (followed by 0–8 per-card data requests in parallel).

---

### L2-043: Goal-progress endpoints answered by single count query
**Traces to:** L1-018

`GET /api/goal-progress/current` and `/at` must each be implemented as a single EF `Achievements.Count(...)` against `Goals.Target` with no in-memory aggregation.

**Acceptance Criteria:**
1. Given the EF query log is captured, when the endpoint is called, then exactly one `SELECT COUNT(*)` is issued and zero `Include`s are present.

---

### L2-044: Scrub debounce ≤ 100ms
**Traces to:** L1-018

`ReviewGoalHistoryController.scrub(pct)` must debounce HTTP calls at 100 ms.

**Acceptance Criteria:**
1. Given 10 scrub events fire in 50 ms, when the debounce settles, then exactly 1 HTTP call is made carrying the *last* `scrubAt`.

---

### L2-045: Historical scrub responses are cacheable
**Traces to:** L1-018

`/api/goal-progress/at` must set `Cache-Control: public, max-age=300` whenever `asOf` is older than 1 minute (historical counts never change).

**Acceptance Criteria:**
1. Given `asOf = UtcNow - 1 day`, when the response is inspected, then `Cache-Control: public, max-age=300` is present.
2. Given `asOf = UtcNow - 10 seconds`, when the response is inspected, then no public cache header is set.

## Modular Architecture

### L2-046: One module per bounded context
**Traces to:** L1-019

The backend solution must contain exactly four feature modules under `backend/src/Modules/`: `Commitments`, `Identity`, `Dashboard`, `DigitalAssets`. Each module is a class library with its own `ModuleExtensions.AddXxxModule(IConfiguration)` consumed once by `Commitments.Api` at startup.

**Acceptance Criteria:**
1. Given the solution is opened, when its project list is enumerated, then exactly the four module projects exist alongside `Commitments.Api` and `Commitments.Shared`.
2. Given any module project, when its references are inspected, then it depends on `Commitments.Shared` only — not on any other module.

---

### L2-047: Cross-module communication via in-process event bus
**Traces to:** L1-019

Modules must not call each other's controllers, services, or DbContexts directly. Cross-module flows must be expressed as `IIntegrationEvent` published on `IEventBus` (in-process pub/sub).

**Acceptance Criteria:**
1. Given a `ProfileCreatedEvent` is published in Identity, when subscribed in Commitments, then the Commitments handler runs synchronously in-process.
2. Given a developer attempts to inject `CommitmentsDbContext` into a Dashboard handler, when the build runs, then there is no project reference path that allows compilation.

---

### L2-048: Vertical slice per feature
**Traces to:** L1-019

Each user-facing feature must consist of: a request DTO, a MediatR `IRequest`/handler pair, a FluentValidation validator (for commands), a controller action that dispatches via MediatR, and (where reads cross transport) a response DTO. Nothing more.

**Acceptance Criteria:**
1. Given a new "Save X" feature is added, when the change is reviewed, then there are no repository, service-layer, or facade classes added on top of the handler — the handler talks to `DbContext` directly.

---

### L2-049: Cross-module references by Guid only
**Traces to:** L1-019

Any reference from one module's entity to another module's entity must be a plain `Guid` foreign key with no navigation property and no `Include` across modules.

**Acceptance Criteria:**
1. Given a Commitments `Activity` references a profile, when the entity is inspected, then it has `ProfileId : Guid` and no `Profile` navigation property.

---
